# Markset v0 — Core Tag Vocabulary

**Status:** Draft. Nothing here is frozen until the conformance suite passes against the reference implementation.

## 0. Scope

This document defines the v0 syntax and tag vocabulary: the grammar for attributes and directives, the eight core block constructs, the reserved class names, the theme token schema, and the degradation contract every construct must satisfy.

It is deliberately small. The v0 bar is: **can a single implementer build a conformant parser and both renderers in a few weeks?** Constructs that fail that bar are listed in §8 with the reason.

Markset is a strict superset of CommonMark. Every valid CommonMark document is a valid Markset document with identical output.

## 1. Design invariants

These govern every decision below. When a proposed feature conflicts with one, the feature loses.

1. **Semantic, never presentational.** Authors name intent (`card`, `metrics`). Appearance comes from the theme. No inline CSS, no color values, no pixel dimensions in document source.
2. **Every construct degrades.** Each one has a defined CommonMark equivalent and a readable raw-source fallback. This is normative, not aspirational — see §3.
3. **Closed vocabulary.** Unknown directive names are a validation error, not silent passthrough. This is what makes documents checkable and makes generated output reliable.
4. **No code execution.** Nothing in v0 evaluates anything.
5. **Reuse convergent syntax.** Attribute specifiers and directive fences already exist in Pandoc, djot, MyST, and remark-directive. Markset adds a vocabulary on top; it does not add a fourth spelling.

## 2. Grammar

### 2.1 Attribute specifier

```
{#id .class .other key=value key2="quoted value"}
```

- Braces contain a whitespace-separated list of items. Whitespace is spaces and tabs; a specifier never spans lines. Leading and trailing whitespace inside the braces is permitted, and `{}` is a valid, empty specifier.
- `#name` sets the id. If repeated, the last wins.
- `.name` appends a class. Repeatable; repeats are kept in order and not deduplicated.
- `key=value` sets an attribute. If repeated, the last wins. Bare values may not contain whitespace, `}`, or quotes (`"` or `'`), and may not be empty; otherwise use double quotes. Backslash escapes `\"` and `\\` inside quoted values; any other backslash sequence is an error. Write `key=""` for the empty string.
- Identifiers match `[A-Za-z][A-Za-z0-9_-]*`. Ids, classes, and keys are all identifiers.
- The keys `id` and `class` are reserved. Use `#name` and `.name`.
- An unrecognized key on a known directive is a validation **warning**; an unknown class is allowed (themes may define their own).

**Parse result.** The AST node is `{ "type": "attributes", "id": <string|null>, "classes": [<string>...], "attrs": { <key>: <value> } }`. All four fields are always present.

**Diagnostics.** A malformed item produces one diagnostic, the parser skips to the next whitespace or `}`, and parsing continues, so one specifier can report several problems. All are errors.

| Code | Trigger |
|---|---|
| `ATTR_UNTERMINATED` | No closing `}` before end of input |
| `ATTR_UNEXPECTED_CHAR` | Item begins with a character that cannot start an item, such as `=` or `"` |
| `ATTR_BAD_IDENTIFIER` | Id, class, or key name does not match the identifier grammar, including an empty name after `#` or `.` |
| `ATTR_EXPECTED_EQUALS` | A key is not followed by `=` |
| `ATTR_EMPTY_VALUE` | `key=` with no value |
| `ATTR_BAD_VALUE` | A bare value contains a quote character, or text follows a quoted value's closing quote |
| `ATTR_UNTERMINATED_QUOTE` | A quoted value has no closing `"` before end of input. Quoted values may contain `}`, so this consumes the rest of the input and `ATTR_UNTERMINATED` is not also reported |
| `ATTR_BAD_ESCAPE` | A backslash in a quoted value is followed by anything other than `"` or `\` |
| `ATTR_RESERVED_KEY` | The key is `id` or `class` |

### 2.2 Bracketed span (inline)

```
[text]{.badge tone=warn}
```

Applies attributes to an inline run. This is the only inline construct in v0 — there are no inline directives. Anything you would express as `:name[text]{}` is expressed as a span with a reserved class instead.

### 2.3 Block directive

```
:::name{#id .class key=value}
content
:::
```

- Opening fence is three or more `:` immediately followed by the directive name.
- An optional bracketed argument may follow the name: `:::card[Pricing tiers]`. Its meaning is per-construct (usually a title). It contains inline content.
- An optional attribute specifier follows the argument.
- The closing fence is a line of at least as many `:` as the opening fence, with nothing else on it.
- Nesting uses longer outer fences, as with code fences.
- Unclosed directives are implicitly closed at the end of the enclosing block. This is a validation warning.
- The name is required. Bare `::: {.foo}` (Pandoc's anonymous fenced div) is **not** valid Markset — the vocabulary is closed.

**Fence lines.** A line whose content, after at most three spaces of indentation, begins with three or more `:` is a fence line. If only whitespace follows the colons it is a closing fence; otherwise it is an opening fence. The name, argument, and attribute specifier follow one another with no whitespace between them, and only whitespace may follow the last part. The name is an identifier (§2.1) and must be one of the block directive names in §4: `card`, `grid`, `columns`, `tabs`, `steps`, `metrics`, `figure`. The argument is raw source text up to the matching `]`; brackets nest, and a backslash-escaped `]` does not close it. It is parsed as inline content later.

**Parse result.** An opening fence is `{ "type": "directive-open", "fence": <int>, "name": <string|null>, "argument": <string|null>, "attributes": <attributes node> }`; `name` is null only when the line is malformed, `argument` is null when no `[...]` is present, and `attributes` is always present, empty when no specifier is written. A closing fence is `{ "type": "directive-close", "fence": <int> }`.

**Diagnostics.** Errors from an embedded attribute specifier are reported with their `ATTR_` codes. The fence line itself adds:

| Code | Trigger |
|---|---|
| `DIRECTIVE_MISSING_NAME` | Opening fence with no name, such as `::: {.foo}` or `:::[Title]` |
| `DIRECTIVE_BAD_NAME` | Name does not match the identifier grammar |
| `DIRECTIVE_UNKNOWN_NAME` | Name is not in the closed vocabulary; `col` is a separator name, not a block name |
| `DIRECTIVE_UNTERMINATED_ARGUMENT` | `[` with no matching `]` on the line |
| `DIRECTIVE_TRAILING_CONTENT` | Anything but whitespace after the last part, including a space before `[` or `{` |

### 2.4 Separator directive

```
::name{attrs}
```

A line of exactly two `:` plus a name. It does not open a block; it separates sibling regions inside a parent directive that declares separator children. In v0 only `::col` exists, inside `:::columns`. Encountered anywhere else, it is a validation error.

This exists so that `columns` doesn't require four levels of fencing to express two columns.

**Separator lines.** A line whose content, after at most three spaces of indentation, is exactly two `:` immediately followed by an identifier, an optional attribute specifier, and nothing else but whitespace. A line beginning with `::` that is not followed by an identifier is ordinary text, not a separator. Separators take no bracketed argument.

**Parse result.** `{ "type": "separator", "name": <string>, "attributes": <attributes node> }`.

**Diagnostics.** `DIRECTIVE_UNKNOWN_NAME` when the name is not `col`, `DIRECTIVE_TRAILING_CONTENT` for anything but whitespace after the last part, and `ATTR_` codes from the specifier. A `::col` outside `:::columns` is `SEPARATOR_OUTSIDE_PARENT`, reported by the document parser rather than the line grammar.

## 3. The degradation contract

Every construct defines two fallbacks. Both are normative and both are covered by the conformance suite.

**Downgrade output.** The result of running the document through the downgrade renderer, which emits plain CommonMark. This is what you get when publishing to a target that has never heard of Markset. The mapping is specified per-construct in §4.

**Naive output.** What a stock CommonMark parser produces from raw Markset source, with no Markset support at all. The spec does not fix the exact output, but requires:

- Content blocks appear in source order.
- Content blocks retain their CommonMark block type — a list stays a list, a table stays a table.
- No construct causes its content to be swallowed, reordered, or absorbed into a code block.
- Fence lines may appear as visible text. This is acceptable. Content mangling is not.

The practical test, and the one worth putting in the README: paste a Markset document into a GitHub comment. It should read as a slightly noisy but complete document, never as syntax soup.

## 4. Core constructs

Eight block constructs. HTML output uses the `ms-` class prefix throughout.

### 4.1 `callout`

Adopts GitHub/Obsidian alert syntax unchanged rather than introducing a directive. This is the single most widely rendered rich-Markdown construct in existence; competing with it would be pure loss.

```markdown
> [!WARNING] Breaking change in v3
> The `render()` signature changed.

> [!NOTE]-
> Collapsed by default.
```

- Types: `NOTE`, `TIP`, `IMPORTANT`, `WARNING`, `CAUTION`. Case-insensitive on input, normalized to uppercase.
- Optional title follows the marker on the same line.
- A trailing `-` marks the callout collapsed by default; `+` marks it expanded. Both are optional.

**HTML:** `<div class="ms-callout" data-type="warning">` containing `<div class="ms-callout-title">` and `<div class="ms-callout-body">`. When a fold indicator is present, emit `<details>`/`<summary>` instead so folding works without JavaScript.

**Downgrade:** a blockquote whose first line is `**Warning:** <title>`.

### 4.2 `card`

```markdown
:::card[Pricing tiers]{tone=info}
Content here.
:::
```

| Attribute | Values | Default |
|---|---|---|
| `tone` | `neutral` `info` `success` `warn` `danger` | `neutral` |
| `compact` | boolean | false |

**HTML:** `<section class="ms-card" data-tone="info">` with an optional `<h3 class="ms-card-title">`.

**Downgrade:** the argument becomes a heading one level below the current section depth; the body follows as ordinary blocks.

### 4.3 `grid`

A list whose items become cards.

```markdown
:::grid{cols=3 gap=md}
- **Fast** — sub-50 ms cold start
- **Small** — 4 kB gzipped
- **Typed** — no `any` in the public API
:::
```

| Attribute | Values | Default |
|---|---|---|
| `cols` | `1`–`4` | `2` |
| `gap` | `sm` `md` `lg` | `md` |

The content **must** be exactly one list. Any other content is a validation error — this is what guarantees the degradation. Renderers reduce `cols` responsively at narrow widths; the exact breakpoints are implementation-defined.

**HTML:** `<div class="ms-grid" data-cols="3">` with one `<div class="ms-grid-item">` per list item.

**Downgrade:** the list, unchanged.

### 4.4 `columns` and `::col`

```markdown
:::columns{ratio="2:1"}
The main argument, at full paragraph length.

::col

:::card{tone=neutral}
A supporting sidebar.
:::
:::
```

| Attribute | Values | Default |
|---|---|---|
| `ratio` | colon-separated integers, one per column | equal |
| `gap` | `sm` `md` `lg` | `md` |

The first column is implicit — content before the first `::col` belongs to it. If `ratio` is present, its term count must equal the column count.

**HTML:** `<div class="ms-columns" style="--ms-ratio: 2 1">` with `<div class="ms-column">` children. This is the one place a style attribute is emitted, because the ratio is genuinely per-instance data.

**Downgrade:** columns emitted sequentially, separated by nothing. Reading order is the source order, which is why authors must put the primary column first.

### 4.5 `tabs`

Headings become tab labels.

```markdown
:::tabs
### macOS
`brew install markset`

### Windows
`winget install markset`
:::
```

- Direct children must be headings at a single consistent level, each followed by its content. Mixed levels are a validation error.
- The first tab is active by default. `active=<n>` overrides.
- Tab state uses radio inputs, not JavaScript.

**HTML:** `<div class="ms-tabs">` with a `<div class="ms-tablist">` of labels and one `<div class="ms-tabpanel">` per section.

**Downgrade:** the headings and their content, unchanged. This is the cleanest degradation in the vocabulary and the reason tabs use headings rather than a `::tab` separator.

### 4.6 `steps`

```markdown
:::steps
1. Install the CLI.
2. Run `markset init`.
3. Edit `markset.toml`.
:::
```

Content must be exactly one ordered list. Nested blocks inside list items are permitted.

**HTML:** `<ol class="ms-steps">` with `<li class="ms-step">`.

**Downgrade:** the list, unchanged.

### 4.7 `metrics`

```markdown
:::metrics
| Metric  | Value | Δ     |
|---------|-------|-------|
| Revenue | $4.2M | +12%  |
| Churn   | 2.1%  | -0.4% |
:::
```

Content must be exactly one table. Column roles are positional: label, value, and an optional delta. A delta cell beginning with `+` or `-` gets a direction attribute; `direction=inverse` flips which sign reads as positive, for metrics like churn where down is good.

**HTML:** `<div class="ms-metrics">` with `<div class="ms-metric">` children carrying `data-direction="up|down"`.

**Downgrade:** the table, unchanged.

### 4.8 `figure`

```markdown
:::figure[Request lifecycle from ingress to response]{#fig-lifecycle width=60%}
![](lifecycle.svg)
:::
```

The argument is the caption. `width` accepts a percentage only — no pixels, no absolute units, because the same source has to typeset to print.

**HTML:** `<figure class="ms-figure" id="fig-lifecycle">` with `<figcaption>`.

**Downgrade:** the image followed by an italic caption paragraph.

## 5. Reserved classes

Available on spans and on any block via an attribute specifier. These are the reason v0 needs no directives for typographic variation.

| Class | Applies to | Meaning |
|---|---|---|
| `.lead` | paragraph | Opening paragraph, larger |
| `.small` | span, paragraph | De-emphasized fine print |
| `.eyebrow` | paragraph | Short label above a heading |
| `.badge` | span | Inline pill |
| `.muted` | any | Reduced emphasis |
| `.info` `.success` `.warn` `.danger` `.neutral` | any | Tone, equivalent to `tone=` |

Themes may define additional classes. Unknown classes pass through to HTML without error.

## 6. Theme tokens

Document-level design intent lives in frontmatter. Token *names* are normative; how a renderer maps them to output is implementation-defined.

```yaml
---
markset: 0
theme:
  preset: editorial       # editorial | technical | deck | report
  accent: "#2563eb"
  density: comfortable    # compact | comfortable | spacious
  radius: md              # none | sm | md | lg
  type:
    body: "Source Serif 4"
    heading: "Inter"
    scale: 1.25
---
```

The `markset:` key declares the spec version and is the recommended trigger for treating a `.md` file as Markset. A document with no `theme` block must still render well; presets carry the load and per-token overrides are the exception.

## 7. Conformance suite

One JSON file per section under `tests/`, mirroring the CommonMark spec test layout, with two extra fields. Each file is an array of cases. The normative schema is [`spec/conformance.schema.json`](conformance.schema.json); the harness validates every file against it before running anything.

```json
{
  "section": "grid",
  "markset": ":::grid{cols=2}\n- One\n- Two\n:::\n",
  "html": "<div class=\"ms-grid\" data-cols=\"2\">...</div>\n",
  "downgrade": "- One\n- Two\n",
  "ast": { "type": "grid", "cols": 2, "children": [] },
  "valid": true
}
```

`valid: false` cases carry a `diagnostics` array naming the expected error codes. Validation failures are a first-class part of the suite, not an afterthought — a closed vocabulary is only worth having if the errors are specified.

Field semantics:

- `section` must equal the file's basename. `name` is an optional human label.
- `markset` is a full document for construct sections (§4). For grammar sections (§2), it is the bare fragment — for `attribute-specifier`, the specifier alone; for `block-directive` and `separator-directive`, a single line without its newline — and `html` and `downgrade` are omitted because a fragment has no rendering. The parser must consume the entire fragment. In the line sections, `"ast": null` asserts that the line is ordinary text, not a directive line.
- `diagnostics` lists every code the parser must emit, errors and warnings alike, in any order. Absent means none are permitted. `valid` is false exactly when at least one listed code is an error.
- `ast` is compared structurally, ignoring object key order. It is required for valid cases and optional for invalid ones, where it pins recovery behavior.
- A case may carry `html` or `downgrade` before the corresponding renderer exists; the harness reports those aspects as skipped, not failed, so cases can be written ahead of the code.

Diagnostic codes are `UPPER_SNAKE`. The first segment names the spec area (`ATTR_`, `DIRECTIVE_`, `GRID_`...). Each diagnostic has a severity of `error` or `warning`; a document is valid when it has no errors.

Every construct in §4 needs, at minimum: a canonical case, a nested case, an empty-content case, a wrong-content-type case (`valid: false`), and an unclosed-fence case.

## 8. Deferred, with reasons

Named here so they don't get relitigated during v0.

- **`chart`** — the most differentiating feature and the most work. Needs a data format decision, a rendering library, and a print story. Ship it as v0.2, designed but not implemented, so the fenced-code syntax is reserved now.
- **`timeline`** — degrades to a list, same as `steps`, and overlaps enough that shipping both invites confusion. Wait for demand.
- **`aside`** (margin notes) — trivial in HTML, genuinely hard in paginated output, which is where it matters most.
- **`pagebreak`** — belongs with a print-layout section that doesn't exist yet.
- **Cross-references and auto-numbering** — a real need and a much larger design surface: reference resolution, numbering schemes, and a link-resolution pass. Deserves its own spec.
- **Inline directives** — bracketed spans plus reserved classes cover every v0 case. Adding them later is backward-compatible; removing them would not be.
- **Interactivity** — out of scope by invariant 4, permanently for the core spec.

## 9. Open questions

1. Should `grid` accept nested `:::card` blocks as an alternative to list items, for cards with multi-block content? It breaks the one-list rule that guarantees degradation. Current answer: no, and use `columns` instead.
2. Does `tabs` need synchronized groups across a page — picking macOS once and having every tab set follow? Common in real docs, but it's state, and state is a slippery slope.
3. Is `markset: 0` in frontmatter the right activation trigger, or should the presence of any directive be enough? Explicit opt-in is safer for files that already use `:::` for something else.
4. Should the downgrade renderer be lossy-but-clean or preserve Markset in HTML comments for round-tripping? Round-tripping is appealing and probably a trap.
